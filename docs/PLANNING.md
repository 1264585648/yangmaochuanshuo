## 1. 现状评估

项目是零依赖的静态前端原型，共 11 个文件、约 300 行。四个卡池、开包动效、每日 3 次、图鉴、收藏、检索都已可交互，全部数据为演示数据。

| 维度     | 现状                                                              | 影响                                          |
| -------- | ----------------------------------------------------------------- | --------------------------------------------- |
| 代码组织 | `app.js` 77 行承载 15KB，单行过长，数据、状态、渲染、事件混在一起 | 难以评审和测试，是后续所有工作的阻碍          |
| 渲染方式 | 模板字符串拼接后写入 `innerHTML`，未转义                          | 演示数据下安全；接入真实福利数据后是 XSS 入口 |
| 抽卡逻辑 | 概率、次数、结果全在浏览器，存 `localStorage`                     | 可被任意篡改，正式版必须移到服务端            |
| 概率定义 | `RARITIES` 表与 `drawRarity()` 中的阈值各写一遍                   | 改一处漏一处，公示概率可能与实际不符          |
| 测试     | 仅 `tests/smoke.mjs` 用正则检查字符串存在                         | 没有行为测试，覆盖率无从谈起                  |
| 工程配置 | 无 `.gitignore`、无 lint、无格式化、无 CI                         | `.idea/` 等本地文件易被误提交                 |
| 数据     | 12 张硬编码演示卡，无来源、有效期、链接字段                       | 产品核心价值尚未开始                          |

## 2. 产品定位与已确认的决策

定位：用「开卡包」的形式做数字福利发现，卡牌是真实公开优惠的索引，不在本站兑现。

以下三点已于 2026-11-11 确认：

1. **账号：分两层（2026-11-12 修订，取代原「暂时不做」）。** 本轮做服务端签发的匿名身份，次数、图鉴、收藏以服务端为准；跨设备登录作为下一层，届时引入开源方案（倾向 GitHub 登录），不自研。用户本机旧数据导入一次（只导图鉴与收藏，校验并限量，次数不导）。详见阶段 3。
2. **数据来源：前期人工维护，同时开放写入接口。** 接口供 AI 巡检程序自动核验、更新和新增福利。人工与 AI 走同一套接口和校验规则。
3. **稀有度：只代表推荐价值。** 目录页全量公开所有卡，抽卡只是趣味入口。

## 3. 技术方向

| 层         | 选择                                               | 理由                                                            |
| ---------- | -------------------------------------------------- | --------------------------------------------------------------- |
| 前端       | 保持原生 JS 与 ES 模块，引入 Vite 仅用于开发与打包 | 页面只有一屏，上框架收益小；Vite 带来模块拆分、热更新和测试集成 |
| 单元测试   | Vitest 加 jsdom                                    | 与 Vite 同配置，可直接测抽卡和存储逻辑                          |
| 端到端测试 | Playwright                                         | README 已列出浏览器交互与视觉回归为上线前必做项                 |
| 后端       | Cloudflare Pages 加 Workers                        | README 已把 Cloudflare Pages 列为部署目标，静态站与接口同域     |
| 数据库     | Cloudflare D1                                      | 福利目录与抽卡记录是小规模关系型数据                            |
| 限流与次数 | KV 或 Durable Objects                              | 每日次数需要原子计数                                            |
| 语言       | 后端用 TypeScript，前端先加 JSDoc 类型检查         | 接口契约需要类型，前端渐进迁移                                  |

D1 的两个已知注意点：免费额度有每日写入上限，抽卡记录要控制写入次数；并发扣次要用单条条件更新语句保证原子性，不能先读后写。

- 过期和失效的卡自动下架，页面显示最后核验日期。

**写入接口与 AI 巡检**

- 写入接口：新增、更新、标记已核验、标记失效。只读接口公开，写入接口需要令牌。
- 令牌按调用方单独签发，保存为 Worker 密钥，可单独吊销。令牌区分权限：巡检令牌只能核验和提交变更，不能直接发布新卡。
- 福利状态机：草稿、待审核、已发布、已失效。AI 新增的卡进入待审核，由人工发布。
- AI 可直接生效的操作只有两类：刷新最后核验日期，把已发布的卡标记为失效。两者都可逆且偏保守。
- AI 修改已发布卡的内容时生成待审核的变更，不直接覆盖线上内容。
- 所有写入经过结构校验：字段长度、枚举值、链接必须为 https。来源链接域名需在提供方登记的官方域名内。
- 每次写入记录审计日志：调用方、时间、变更前后内容、依据的来源链接。支持按记录回滚。
- 写入接口限流，并按幂等键去重。
- 巡检程序本身是独立的定时任务，不属于本仓库的首要交付。本阶段先交付接口和一份接口说明，巡检程序随后单独实现。

完成标准：目录页全部为真实数据，每条有来源链接和核验日期。用巡检令牌无法直接发布新卡或改写线上内容，所有写入可在审计日志中查到。

### 阶段 3：轻量用户体系与服务端抽卡（U1–U3 已上线，U4 可选）

用户体系与服务端抽卡合并实施：抽卡、扣次、图鉴都在浏览器里时，单独加身份没有意义。

**要修正的不规范之处**

| 问题     | 原状                                             | 改为                                                                 |
| -------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| 日界     | 前端按设备本地日期，Worker 按 UTC                | 服务端统一按北京时间 0 点重置，接口返回 `resetsAt`                   |
| 次数     | 存在浏览器、可篡改、清存储即恢复；上限写死在前端 | 服务端单条条件语句扣次，上限在服务端配置                             |
| 图鉴     | 实为最近 100 条抽卡历史，抽多了旧卡被挤掉        | 图鉴是「抽到过的卡」集合，不设上限；历史单独分页查询                 |
| 图鉴进度 | 分母是当前有效卡、分子剔除过期卡，数字会漂移     | 已发现按当前有效卡计；已下架的卡仍显示并单独计数；按池与稀有度给进度 |
| 收藏     | 仅大厅可用，仅存本机                             | 跟随用户存服务端                                                     |

**身份**

- A 层（本轮）：首次抽卡时服务端签发随机令牌，放在 HttpOnly、Secure、SameSite=Lax 的 Cookie 中，D1 只存哈希。只浏览不抽卡不建用户。
- B 层（按需）：同一用户行上挂登录凭证，首次登录时把匿名用户的数据合并进账号。

**数据表**：`users`、`sessions`、`draws`（唯一事实来源，索引 `(user_id, day)`，唯一 `(user_id, idem_key)`）、`favorites`。扣次与写记录为同一条 `INSERT … SELECT … WHERE 当日次数 < 上限`；图鉴由 `draws` 按卡聚合得出。福利卡不物理删除，已下架的卡在图鉴中仍可关联。

**接口**：`GET /api/me`、`POST /api/draws`（幂等键）、`GET /api/me/collection`、`GET /api/me/draws`、`PUT/DELETE /api/me/favorites/:offerId`、`POST /api/me/import`。带 Cookie 的写请求校验 Origin、SameSite 与 JSON 内容类型；`/api/me*` 一律 `no-store`；按 IP 哈希限制新建用户数与抽卡总量，不存原始 IP。

**分步**

1. U1 身份与数据表：迁移 `0004_users.sql`、Cookie 会话、`GET /api/me`、Origin 校验。完成标准：签发、识别、过期、吊销有集成测试。
   - 实际结果（2026-11-12）：新增 `users`、`sessions` 两表；`worker/src/auth/session.ts` 负责签发、识别、续期（满 30 天续一次）、吊销，`last_seen_at` 每天最多写一次；`worker/src/users/day.ts` 按北京时间计算日界与 `resetsAt`；`/api/me*` 统一经 Origin 校验后路由。签发与吊销暂无对外接口，在模块层用真实本地 D1 测试；首次签发随 U2 的抽卡接口接入。前端尚未改动。
2. U2 服务端抽卡与扣次：`POST /api/draws`，含幂等与 IP 限流；只从当前有效的卡中抽取，按实际卡池动态计算并公示概率。完成标准：篡改浏览器存储无法增加次数或伪造结果；并发扣次与重放有测试。
   - 实际结果（2026-11-12）：迁移 `0005_draws.sql`；`POST /api/draws` 按「校验 → IP 限流 → 幂等重放 → 空池拒绝 → 按需建匿名用户 → 单条条件插入」处理，`GET /api/me` 增加 `quota.used`。概率与选卡复用前端 `src/domain/catalog.js`，公示与实际同源。IP 用 HMAC（密钥 `IP_HASH_SECRET`）哈希后计数，缺密钥时抽卡拒绝服务。已在本地 `wrangler dev` 用 curl 实测新建、重放、扣满与跨站拒绝；另用手工设置 `Host`/`Origin` 的请求模拟 Vite 代理，同源判断通过（未经真实浏览器与代理）。前端仍走本地抽卡，切换放在 U3。
   - 安全审查后已处理：IPv6 按 /64 合并限流；已有会话的重放与次数用尽不占用 IP 额度；`IP_HASH_SECRET` 至少 32 字符。留待后续：
     - 定时清理过期的 `rate_limits` 行、过期会话与没有抽卡记录的匿名用户（2026-11-12 已加，见阶段 4）。
