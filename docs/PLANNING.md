# DealDex · 福利传说 前期规划

> 编写日期：2026-11-11。基于提交 `1cc599d` 的代码现状。
> 与 `docs/IMPLEMENTATION.md` 的关系：那份文档记录第一阶段做了什么，本文档规划接下来怎么走。

## 1. 现状评估

项目是零依赖的静态前端原型，共 11 个文件、约 300 行。四个卡池、开包动效、每日 3 次、图鉴、收藏、检索都已可交互，全部数据为演示数据。

| 维度     | 现状                                                              | 影响                                          |
| -------- | ----------------------------------------------------------------- | --------------------------------------------- |
| 代码组织 | `app.js` 77 行承载 15KB，单行过长，数据、状态、渲染、事件混在一起 | 难以评审和测试，是后续所有工作的阻碍          |
| 渲染方式 | 模板字符串拼接后写入 `innerHTML`，未转义                          | 演示数据下安全；接入真实福利数据后是 XSS 入口 |
| 抽卡逻辑 | 概率、次数、结果全在浏览器，存 `localStorage`                     | 可被任意篡改，正式版必须移到服务端            |
| 概率定义 | `RARITIES` 表与 `drawRarity()` 中的阈值各写一遍                   | 改一处漏一处，公示概率可能与实际不符          |
| 测试     | 仅 `tests/smoke.mjs` 用正则检查字符串存在                         | 没有行为测试，覆盖率无从谈起                  |
| 工程配置 | 无 `.gitignore`、无 lint、无格式化、无 CI                         | `.idea/` 等本地文件易被误提交                 |
| 数据     | 12 张硬编码演示卡，无来源、有效期、链接字段                       | 产品核心价值尚未开始                          |

## 2. 产品定位与已确认的决策

定位：用「开卡包」的形式做数字福利发现，卡牌是真实公开优惠的索引，不在本站兑现。

以下三点已于 2026-11-11 确认：

1. **账号：暂时不做。** 次数限制按匿名设备标识加 IP 做弱限制，收藏留在本地。后期需要时引入开源方案，不自研。数据表从一开始预留可空的用户标识字段，避免将来迁移。
2. **数据来源：前期人工维护，同时开放写入接口。** 接口供 AI 巡检程序自动核验、更新和新增福利。人工与 AI 走同一套接口和校验规则。
3. **稀有度：只代表推荐价值。** 目录页全量公开所有卡，抽卡只是趣味入口。

## 3. 技术方向

| 层         | 选择                                               | 理由                                                            |
| ---------- | -------------------------------------------------- | --------------------------------------------------------------- |
| 前端       | 保持原生 JS 与 ES 模块，引入 Vite 仅用于开发与打包 | 页面只有一屏，上框架收益小；Vite 带来模块拆分、热更新和测试集成 |
| 单元测试   | Vitest 加 jsdom                                    | 与 Vite 同配置，可直接测抽卡和存储逻辑                          |
| 端到端测试 | Playwright                                         | README 已列出浏览器交互与视觉回归为上线前必做项                 |
| 后端       | Cloudflare Pages 加 Workers                        | README 已把 Cloudflare Pages 列为部署目标，静态站与接口同域     |
| 数据库     | Cloudflare D1                                      | 福利目录与抽卡记录是小规模关系型数据                            |
| 限流与次数 | KV 或 Durable Objects                              | 每日次数需要原子计数                                            |
| 语言       | 后端用 TypeScript，前端先加 JSDoc 类型检查         | 接口契约需要类型，前端渐进迁移                                  |

D1 的两个已知注意点：免费额度有每日写入上限，抽卡记录要控制写入次数；并发扣次要用单条条件更新语句保证原子性，不能先读后写。

## 4. 分阶段路线

### 阶段 0：工程地基（已完成）

- 添加 `.gitignore`，覆盖 `.idea/`、`node_modules/`、`dist/`。
- 引入 Prettier 与 ESLint，先格式化现有三个源文件，单独一次提交。
- 引入 Vite 与 Vitest，保留 `npm run dev` 与 `npm run check` 两个入口。
- 添加 GitHub Actions：lint、测试、构建。

完成标准：新克隆后 `npm install && npm run check` 通过，CI 为绿。

实际结果：Vite 8、Vitest 5、ESLint 10、Prettier 3，Node 要求 22.13+、24 或 26+（与 Vitest 一致）。原有零依赖服务器保留为备用预览方式。本地 `npm run check` 与 GitHub Actions 均已通过（提交 `a4c84a8`）。

### 阶段 1：前端重构，行为不变（已完成）

把 `app.js` 拆成小模块，先补测试再搬代码：

```text
src/
  data/pools.js        卡池定义
  data/offers.js       演示福利
  domain/draw.js       稀有度抽取与选卡，随机源可注入
  domain/quota.js      每日次数，日期可注入
  storage/local.js     localStorage 读写与校验
  ui/packs.js          卡包渲染与切换
  ui/dialog.js         弹窗与焦点管理
  ui/views.js          结果、图鉴、检索、概率
  ui/escape.js         HTML 转义
  main.js              装配与事件绑定
```

- 概率只保留 `RARITIES` 一处定义，抽取函数从表计算。
- 所有动态文本经过转义后再进入 HTML。
- 状态更新改为返回新对象，不原地修改。
- 单元测试覆盖抽取分布、跨日重置、存储损坏回退、转义。

完成标准：页面表现与当前一致，领域与存储模块覆盖率不低于 80%。

实际结果：

- 按上表拆分，另增 `src/config.js`（常量）、`src/domain/collection.js`（图鉴、收藏、检索）、`src/ui/icons.js`（可信 SVG）；弹窗与提示合并在 `src/ui/dialog.js`。
- `tests/main.integration.test.js` 在 jsdom 中加载真实 `index.html` 驱动整页：选池、开包、扣次、收藏、概率、图鉴、检索、次数用尽。该测试先对旧 `app.js` 运行作为基线，10 项中 9 项通过，唯一失败即下述已修复的缺陷。
- `vite.config.js` 对 `src/domain/`、`src/storage/` 与 `escape.js` 设置 80% 覆盖率门槛，由 `npm run coverage` 检查。
- 与旧版的行为差异（均为修复）：其他标签页写入损坏数据时，旧版报错崩溃，现经校验后回退为空；存储中的非法收藏、图鉴条目会被过滤；卡池无可抽卡时提示而不是报错（演示数据下不会出现）。
- 稀有度映射改为按表累计阈值（随机值小于 0.7 为 A），分布不变，但同一随机值对应的等级与旧版不同。

### 阶段 2：真实福利目录与写入接口（进行中）

- 定义福利数据模型：标题、提供方、类别、稀有度、领取条件、官方链接、来源、最后核验日期、有效期、状态。
- 条件字段结构化：新用户、学生身份、地区、是否需要支付方式、是否自动续费。
- 建 D1 表与只读接口：列表、筛选、详情。
- 前端「发现优惠」改为独立可链接的目录页，支持筛选，利于搜索引擎收录。
- 准备首批真实数据，每个卡池至少 10 条，逐条人工核验。
- 过期和失效的卡自动下架，页面显示最后核验日期。

**写入接口与 AI 巡检**

- 写入接口：新增、更新、标记已核验、标记失效。只读接口公开，写入接口需要令牌。
- 令牌按调用方单独签发，保存为 Worker 密钥，可单独吊销。令牌区分权限：巡检令牌只能核验和提交变更，不能直接发布新卡。
- 福利状态机：草稿、待审核、已发布、已失效。AI 新增的卡进入待审核，由人工发布。
- AI 可直接生效的操作只有两类：刷新最后核验日期，把已发布的卡标记为失效。两者都可逆且偏保守。
- AI 修改已发布卡的内容时生成待审核的变更，不直接覆盖线上内容。
- 所有写入经过结构校验：字段长度、枚举值、链接必须为 https。来源链接域名需在提供方登记的官方域名内。
- 每次写入记录审计日志：调用方、时间、变更前后内容、依据的来源链接。支持按记录回滚。
- 写入接口限流，并按幂等键去重。
- 巡检程序本身是独立的定时任务，不属于本仓库的首要交付。本阶段先交付接口和一份接口说明，巡检程序随后单独实现。

完成标准：目录页全部为真实数据，每条有来源链接和核验日期。用巡检令牌无法直接发布新卡或改写线上内容，所有写入可在审计日志中查到。

进度：

- 已完成：数据模型与 D1 迁移、公开只读接口、管理写入接口（令牌、状态机、变更申请、审计与回滚、幂等、限流）、令牌管理脚本、接口说明 `docs/API.md`。
- 实现与规划的差异：
  - 部署形态改为 Workers 加静态资源，一次部署同时包含前端与接口。接口写成 `fetch(request, env)`，需要时可加薄适配层迁回 Pages。
  - 令牌哈希存在 D1 的 `api_clients` 表，而不是 Worker 密钥。签发和吊销不需要重新部署，原文同样只显示一次。
  - 写入的原子性：条件更新后插入 `changes()` 到 `write_guard` 表，由触发器在未命中时中止整批，使内容、审计、幂等记录要么全部写入，要么全部不写（`migrations/0002_write_guard.sql`）。
  - 测试用 wrangler 的 `getPlatformProxy` 在 Vitest 5 中运行真实本地 D1，因为官方 Workers 测试插件只支持 Vitest 4。
- 前端已接入真实接口（2026-11-11）：移除内置演示数据；大厅、结果、详情、图鉴、概率与「发现优惠」全部读 `/api/offers`；补齐载入、空池、失败重试、离线恢复与过期刷新状态；概率按各池实际有卡的等级换算并公示；开包与揭晓动效重做。本地用 `npm run db:seed:local` 写入虚构示例数据开发。
- 目录页已独立（2026-11-11）：「发现优惠」从弹窗改为可直接访问的 `/offers`，单卡页为 `/offers/<id>`。
  - 筛选（卡池、稀有度、新用户、学生、支付方式、自动续费、关键词）和页码都写在网址里，刷新、分享、浏览器前进后退都能还原。参数名与 `GET /api/offers` 一致。
  - 搜索引擎收录：Worker 从 D1 直接渲染整页 HTML，包含每页独立的标题、描述、canonical 与 robots。筛选表单是普通 GET 表单，分页是真实链接，不运行脚本也能浏览全部福利。另由 Worker 提供 `/sitemap.xml`（目录、各卡池与每张有效福利）和 `/robots.txt`。浏览器脚本只接管后续跳转，用同一套模板函数渲染，两端输出一致。
  - 下架与核验：列表和单卡页只显示已发布且在有效期内的卡。已过期、已失效或不存在的卡返回 404 页面并标记 noindex，同时从站点地图中消失。每张卡显示来源链接和最后核验日期（绝对日期，缓存后不会失真，未核验的卡标明「尚未核验」）。
  - 索引策略：全量目录和单个卡池的页面允许收录；关键词搜索、稀有度与条件组合可链接但标记 noindex，避免大量近似页面。
  - 与规划的差异：公开接口没有地区筛选，地区只作为卡片上的条件标签显示。
- 待完成：首批真实数据（采用方案 b：按官方页面整理候选卡，全部以待审核状态入库，人工核验后发布）；Cloudflare 账号下创建远程数据库与部署。

### 阶段 3：服务端抽卡（约 1 周）

- 抽卡接口在服务端完成随机、扣次、记录，放在同一个原子操作里。
- 每次请求带幂等键，防重放和重复扣次。
- 只从当前有效的卡中抽取，按实际卡池动态计算并公示概率。
- 匿名设备标识加 IP 限流。抽卡记录表预留可空的用户标识字段，供后期接入开源账号方案。
- 前端处理离线、超时、次数用尽、卡池为空四种失败情况。
- 接口集成测试覆盖并发扣次与重放。

完成标准：篡改浏览器存储无法增加次数或伪造结果。

### 阶段 4：上线准备（约 1 周）

- Playwright 覆盖核心流程：选池、开包、看结果、收藏、图鉴、检索。
- 响应式视觉回归：1440×900、平板、手机三档。
- 无障碍检查与 Lighthouse 性能检查。
- 隐私说明、免责声明、概率公示页。
- 域名、缓存策略、错误监控。

## 5. 风险

| 风险                                | 级别 | 应对                                                             |
| ----------------------------------- | ---- | ---------------------------------------------------------------- |
| 福利信息过期或不实，误导用户        | 高   | 人工核验、显示核验日期、到期自动下架、用户反馈入口               |
| 抽卡形式的合规问题                  | 中   | 坚持不付费、公示真实概率、目录全量可查                           |
| 第三方品牌名称与商标的使用          | 中   | 仅做信息性引用并链接官方页面，不使用官方标志暗示合作             |
| 无账号下的刷次数                    | 中   | 抽卡不发放实际价值，刷次数收益低；限流即可                       |
| 接入真实数据后的 XSS                | 中   | 阶段 1 完成统一转义，录入端做校验                                |
| AI 巡检写入错误或被诱导写入恶意内容 | 高   | 新卡和内容变更必须人工审核，官方域名白名单，结构校验，审计与回滚 |
| 写入令牌泄露                        | 中   | 按调用方分发、最小权限、可单独吊销、限流                         |
| 重构引入回归                        | 低   | 阶段 1 先写测试再拆分                                            |
